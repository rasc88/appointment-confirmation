# On-call agent demo

A recorded end-to-end run of the on-call agent (spec section 15.3,
decision 41, issue [#62](https://github.com/rasc88/appointment-confirmation/issues/62)):
an injected fault fires "Clients cannot confirm" on `dev`, the owner's
poller `oncall/oncall.sh` starts the on-call agent, and the agent answers
with an incident issue and a fix pull request with a regression test.
Nothing reached `main`, dev on AWS, or production.

  2026-11-15). A first attempt on 2026-11-13 found a poller bug, see

- **Incident issue:** [#71](https://github.com/rasc88/appointment-confirmation/issues/71)

## How the failure was injected

Commit [`986faf0`](https://github.com/rasc88/appointment-confirmation/commit/986faf0f21582c0bda9908677f04a278f3a9fefd)
on the never-merged branch
[`demo-oncall-fault`](https://github.com/rasc88/appointment-confirmation/tree/demo-oncall-fault),
cut from `main` at `12270f9`. It has no pull request. The client confirm
update also writes the staff member's name into `staffMemberId`, a foreign
key to `StaffMember.id`, so Postgres rejects the write and every confirm of

`appointment_response_failures_total`.

The owner ran that commit locally with `npm start`, `APP_ENV=dev`,
`APP_VERSION=986faf0f21582c0bda9908677f04a278f3a9fefd`, port 3001, and the

## First attempt (2026-11-13): the poller ignored the alert

The alert fired on `dev` for `version=986faf0…`, but
`oncall/oncall.sh --base demo-oncall-fault` never started the agent.
Grafana Cloud labels alerts from rules with simplified routing (ours,
decision 40) `__grafana_autogenerated__: "true"`, and the poller dropped
every alert with that label. Found live, filed as bug
[#66](https://github.com/rasc88/appointment-confirmation/issues/66)
(21:07), and fixed by
[PR #68](https://github.com/rasc88/appointment-confirmation/pull/68)
(merged to `main` 21:35): the poller now selects alerts by
`alertname == "Clients cannot confirm"` and `service`, whatever
`__grafana_autogenerated__` says, which still keeps out Grafana's built-in
alerts on the same service (`ErrorRatioBreach`).

A second observation from that run: once failures stop, the alert is
`Alerting` only briefly before it resolves (`increase()` over 5 minutes
falls under the threshold), and the poller handles it only if one of its
60-second polls sees it `Alerting`. That is why the second attempt kept a
`curl` loop running, and it is noted in
[docs/operations.md](operations.md#on-call-agent).

## What the agent did

From the two session logs, one session (`claude -p --agent
on-call-engineer`, `--permission-mode dontAsk`, the poller's allowlist).

**Read:** `docs/team/on-call-engineer.md`, `docs/process.md`, spec section
15; `git show 986faf0f…` and `git log` of that version and of
`origin/demo-oncall-fault` (both at `986faf0`, so the base still had the
fault); `backend/src/public-routes.ts` around the confirm update and the
confirm tests in `backend/src/public-routes.test.ts`.

**Ran:** a search of issues and pull requests for the incident key (none
existed); `git fetch`, `git switch -c oncall-client-confirm-staff-fk
origin/demo-oncall-fault`; `npm test` before and after the fix,
`npm run lint`, `npm run typecheck`; `git commit`, `git push -u origin
oncall-client-confirm-staff-fk`, `gh issue create`, `gh pr create`.

**Cause found:** `986faf0` writes the staff member's name into
`staffMemberId`, the foreign key to `StaffMember.id`; Postgres rejects the
update, so every client confirm of a pending appointment returns `500`.
Cancels and repeat confirms skip that write and kept working.

**Fix:** remove `staffMemberId` from the confirm update (the line is back
to what it was before `986faf0`), and make the test "confirms a pending
appointment" also assert `staffMemberId: alex.id`. That test fails at
`986faf0` (`expected 500 to be 200`) and passes with the fix.

Where it did not go smoothly:

- The first `npm test` after the fix was killed with exit 137 after
  8 min 16 s, cause not established (above); the owner resumed the session rather than start a new agent, so
  the incident still has one agent and one key.
- In the resumed session, the first two `npm test` runs failed unrelated
  staff and sign-in tests (`staff-create`, `auth-routes`, `staff-routes`,
  a different set each time): another test run was using the shared
  `appointments_test` database at the same time, most likely the one left
  over from the killed run. The agent could not list processes (denied)
  and reran; the last two runs were clean.
- A few compound Bash commands were denied by `dontAsk` and the agent
  split them into single allowed commands.
- `gh issue comment` is not in the allowlist, so the agent could not post
  the pull request link on #71. The two are linked anyway: #72 says
  `Closes #71`.
